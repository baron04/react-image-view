This page records the decisions behind the defaults — what was chosen, and
what was deliberately left out.

## Review-oriented, not gallery-oriented

The library is built for looking at document attachments and admin image
fields — 1 to maybe 5 images per set, opened to check something specific.
That's a different job from a photo gallery, and several conventions
gallery libraries treat as default were deliberately left out or narrowed:

- **No autoplay slideshow.** Nobody wants a purchase-order scan to advance
  itself.
- **No image editing, no gallery/grid layout.** Both are out of scope by
  design — pair a grid layout library with this for the "before" half of
  the flow.
- **Swipe-to-dismiss only responds to touch and pen.** It shipped
  responding to any pointer at first, including a mouse — dragging
  downward on a desktop is not a "close this" gesture anywhere else, and a
  stray drag closing the viewer cost the reader their place for nothing.

## Why the counter and thumbnails are off by default

Both answer "how many, where am I" — a real question in a 40-photo gallery,
much less of one across the 1–5 attachments this library is built around,
where the arrows already say whether there's more. Both are one prop away
(`counter`, `thumbnails` on `DefaultContent`) for the sets where they do
earn their space.

## Two buttons, not a segmented control

`FitToWindow` and `ActualSize` look like they'd make a natural segmented
control — "fit" or "100%," pick one. They're two independent buttons
instead, because a segmented control asserts one option is always
selected, and that's false here: at 173% zoom, neither is the current
state. Modelling that as a segmented control means inventing a third,
unselected state the component doesn't actually support.

## "1:1" as a lettered icon, not text

Every other toolbar control is a wordless icon; `ActualSize` needs to say
something more specific than a magnifying glass can. Plain text made it
the one visual outlier in an all-icon row. A wordless pictogram (a pixel
grid, a pair of nested frames) turned out to have no agreed-on meaning to
lean on — people guessed crop tool, grid overlay, aspect ratio, anything
but "actual size." The shipped icon draws the two characters `1:1` inside
a stroked frame, keeping the same outline weight as its neighbours while
staying legible without a tooltip.

## Two ways to get the design

The same visual design ships two ways, because "restyle with plain CSS" and
"own Tailwind source in my repo" are different needs:

**The CSS preset** (`react-img-view/styles.css`) — custom properties on
`:root` and the dialog itself, works with any styling approach, zero build
requirements. See [Installation](../installation/#styles).

**The shadcn registry block** — the same composition, restyled with
Tailwind utility classes, installed as real editable source via
`npx shadcn add https://baron04.github.io/react-img-view/r/image-view.json`.
Behaviour (gestures, the modal, keyboard, the open/close animation) stays a
real `react-img-view` dependency; only presentation is copied into your
project — the same split shadcn's own blocks use for Radix.

Both encode the same design tokens as two different mechanisms (CSS custom
properties vs. Tailwind arbitrary values fed by the registry's `cssVars`),
which means a palette change has to happen in both places. That's a real,
accepted cost of offering both — not an oversight.
