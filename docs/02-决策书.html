交互拆解

飞书那三张图告诉我们什么

先把它的结构拆开：顶栏是实体栏（不是浮层），左侧 ✕ Close 带文字标签、竖线分隔，然后是文件类型色标 + 文件名 + 次级色的文件大小；右侧两个描边按钮。舞台在浅色模式下是浅冷灰而不是黑遮罩，暗色模式下是纯黑。图片 contain 居中，四周留白很足，无阴影无边框。翻页按钮是浮在舞台边缘的圆形按钮。底部是一个独立的胶囊工具栏，五个线性图标——缩小、放大、旋转、1:1、下载——悬停出深色带箭头的 tooltip。

值得学的

  1. 浅色模式用浅灰舞台，不用黑遮罩它"不像传统 lightbox"、显得现代，主要就来自这一个决定。黑遮罩是 2010 年代的语言。
  2. 顶栏承载文件元信息文件名、大小、类型色标。让预览有"文件感"而不只是"图片感"。
  3. 加载态里顶栏和翻页按钮先在位只有舞台是空的。元信息先于图片可用，布局不跳动。
  4. 到边界时翻页按钮隐藏而非禁用比灰掉的禁用态干净，也少一次无效点击。
  5. tooltip 统一深色带箭头纯图标工具栏必须配的东西，它做到位了。

我们要改掉的

  1. 没有计数器多图时不知道总共几张、当前第几张。成本极低而信息价值极高，这是它最明显的漏洞。
  2. 下载按钮出现两次顶栏一个 Download，底部工具栏又一个下载图标。功能重复，操作重心分裂在屏幕上下两端。
  3. 没有缩放比例反馈放大后不知道当前几倍，也不知道离上限还有多远。
  4. 大屏上图片太小留白过多且没有"适应窗口"的默认放大策略，4K 屏上浪费严重。
  5. 两个模式明度差过大浅色浅灰、暗色纯黑，同一个组件像两套设计。
  6. 五个图标全靠 tooltip 认1:1 这种图标离开 tooltip 基本无法识别。

你问的问题

缩略图要不要做：要，但默认自动

飞书不做缩略图是对它的场景正确——多维表格一条记录挂 1 到 3 个附件，一条缩略图轨是纯浪费。但我们是通用组件，场景里包含相册、商品图、文档配图，图一多，没有缩略图轨就是硬伤：用户既不知道有几张，也无法跳转。

所以拆成两件事，不要混为一谈：

  • 计数器进 P0。就是 3 / 12 这么一行字，实现成本接近零，解决"有几张、我在哪"。飞书缺这个是它的失误，不是它的取舍。
  • 缩略图轨进 P1，默认 auto。单图不渲染，多图才出现；提供 always / never 强制。窄屏默认隐藏——移动端一条缩略图轨要吃掉 15% 的屏幕高度，不划算。

这样单图场景的用户拿到的是飞书那种干净界面，相册场景的用户不用自己造轮子。默认值替用户做了对的决定，这是好 API 的标志。

场景定位

审阅型，不是欣赏型

主场景定为文档附件与后台管理系统的图片字段。这两个看起来是两件事，实际是同一类——用户打开图片不是为了欣赏，是为了核验：这张凭证的编号是多少、这份扫描件的字看不看得清、这张截图有没有被压糊、这是不是用户该传的那份材料。

这个定性把整个产品的取向定死了，而且和相册类产品几乎处处相反：

审阅型（我们）欣赏型（相册 / 社交）
用户目标看清细节、核对、留存沉浸、浏览、分享
工具栏常驻可见自动淡出
缩放要档位、要比例数字连续无级即可
1:1 原始尺寸核心功能几乎无用
文件元信息必需（名称 / 大小 / 类型）可有可无
主要输入鼠标 + 键盘触摸手势
旋转高频（手机拍的凭证是歪的）低频
幻灯片播放没人要常用
图片张数通常 1–5 张几十上百张

这条定位修正了我之前的一处偏向：我原本把重心押在移动端手势上（因为那是竞品最弱的地方），但你的主场景是桌面端审阅。手势仍然是 P0——它是技术护城河，也是移动端的基础——但桌面端的键盘与精确控制必须提到同等地位，不能只顾手感。

对照组修正

我们真正的竞品不是灯箱库

同一个方法错误还波及了竞品分析。前一份市场调研把 YARL、react-photo-view、PhotoSwipe、lightGallery 放在一起比——那是欣赏型画廊的对照组。但一个要在后台管理系统里加图片预览的开发者，手上已经有 antd 了，他不会去装一个灯箱库。

数据是明摆着的：

库周下载形态和我们的关系
rc-image antd 内置2,489,663组件库自带预览真正的默认选项——用户不需要做任何决定就得到它
viewerjs117,648审阅型 vanilla同类型，功能对照的基准
react-viewer26,153审阅型 React唯一的同形态 React 竞品，已失修
yet-another-react-lightbox547,112欣赏型画廊不同形态，之前被我当成主要对手

rc-image 的 249 万周下载不是靠它做得多好，是靠它零决策成本。这把 README 的第一个问题从「为什么选我们而不选 YARL」换成了一个难得多的问题：

我已经在用 antd 了，为什么还要多装一个包？

答不上这个问题，项目就没有存在理由。目前能站住的答案有三条，都要在 v1 里真的做到，而不只是写在 README 上：

  • 不绑定组件库。antd 的预览只服务 antd 用户；arco、semi、MUI、shadcn、无组件库的项目各自重复造轮子。我们是那个横跨所有人的选项。
  • 手势质量。rc-image 的移动端手势是能用级别，没有惯性、没有回弹、缩放态不能滑动切图。这是最难被追平的一条。
  • 可定制到底。headless + 可拷贝源码，对上 rc-image「只能改几个 props」的天花板。

相应地，功能上有一条隐含要求：凡是 antd 预览有的，我们不能缺（缩放、旋转、翻页、键盘、镜像翻转）。缺一样就给了用户不迁移的理由。镜像翻转因此要补进 P1——之前整个漏掉了，因为我对照的是灯箱库，而灯箱库都没有这个功能。

明确不做

非目标和目标一样重要，这几条写进 README，不接需求：

  • 幻灯片自动播放。审阅场景没有这个动作——没人会让凭证自动轮播。YARL 和 lightGallery 都带这个功能，我们明确不跟。
  • 不做图片编辑。裁剪、标注、批注属于另一个产品，一旦沾上边界就守不住了。
  • 不做画廊布局。瀑布流、网格排版交给 react-photo-album 那类组件，我们只负责「点开之后」。

为什么 1:1 必须配一个「适应窗口」

飞书只有 1:1，没有适应窗口——放大之后没有一键回到初始状态的按钮，只能一直点缩小。这两个是一对，必须成对出现：1:1 回答「原始像素下清不清楚」，适应窗口回答「让我重新看全貌」。审阅动作就是在这两个状态之间来回切。

键盘快捷键分两档，不要假装都是通用的

这一节原本写的是「直接复用 Preview / Figma / Photoshop 那套」——那是拿错了对照组：那几个是专业创作工具，它们的用户和审单据的后台用户不是同一批人，肌肉记忆不通用。按真实认知成本分两档：

核心Esc关闭同上

核心档三个键必须有，进阶档三个键做出来但不在界面上宣传——tooltip 里带着，会用的人自然会用，不会用的人靠按钮也能完成全部操作。没有任何功能只能通过进阶快捷键抵达。

技术决策

十条，附实测数据

01

弹层用原生 <dialog>，不用 Portal 手搓

支持率 96.11%

理由showModal() 免费给到四样东西：top layer（永远在最上层，彻底退出 z-index 战争）、焦点陷阱、ESC 关闭、::backdrop。手搓 Portal 这四样每一样都是坑。

额外收益YARL 有一条"在 Dialog 里用 lightbox"的未解决讨论——原生 top layer 天然支持嵌套弹层，这个问题在我们这里不存在。

风险iOS Safari 15.4–16 的 showModal() 有边缘 bug，需要早期真机验证并准备降级路径。

02

手势三层状态机 + 边缘接力

核心竞争力

模型三层各自独立，按优先级消费同一串指针事件：

  • Pager（横向翻页）· Pan（缩放态平移）· Pinch/Wheel（缩放）

关键规则缩放态下横向拖动先给 Pan 消费；当图片在该方向已经顶到边界，把剩余位移移交给 Pager。微信、飞书的移动端图片预览都是这个行为（iOS 照片同理，但同形态的对照是前两者），也正是 YARL 那条"Zoom blocks swipe until fully zoomed out"缺的东西。下拉关闭只在 scale === 1 时激活，避免和平移打架。

基础Pointer Events（96.08%，Safari 13+）+ setPointerCapture + 舞台 touch-action: none。不碰 touch events。

风险这是全项目最大的隐性成本。手感调参（阈值、阻尼、速度采样窗口）没有捷径，预留 30% 工时，且必须在真机上调。

03

不引入动画库，自己写弹簧

理由framer-motion 周下载 4,397 万，但作为核心依赖体积太大。惯性用速度采样 + 指数衰减，回弹用临界阻尼弹簧，transform: translate3d + scale 在 rAF 里批量提交，全程不触发 layout。自己写大约 200 行，换来零依赖。

对标react-photo-view 7.5 kB gzip、YARL 11.7 kB。我们的目标：核心 < 10 kB，零运行时依赖。

04

开合动画用 FLIP 兜底，View Transitions 作为可选项

VT 仅 90.20%

数据View Transitions（同文档）Chrome 111、Safari 18、Firefox 要到 144，全球 90.20%。低于我们其他所有底座技术。

决策默认走 FLIP（getBoundingClientRect 反算 transform），全浏览器一致且完全可控；View Transitions 做成 transition="view-transition" 的 opt-in。不把观感一致性押在 90% 上。

05

缩放上限动态计算，不写死 maxScale

竞品崩溃点

病根react-photo-view 有一条"预览某些图片导致浏览器崩溃"的未修 issue。根因是 CSS transform 放大 <img> 时浏览器要按放大后的尺寸重新栅格化，显存直接爆掉。它还有一条相反的 issue：大图被 maxScale: 6 卡住，放到头都不到原始尺寸。写死上限两头都错。

对策上限 = 图片原始像素 ÷ 当前渲染像素，让"放到 100%"永远可达且不越界；will-change: transform 只在手势期间挂载，手势结束立刻摘掉（长期挂着会持续占显存）；切图前先 img.decode() 再提交，消除白闪。

06

滚动锁定：overscroll-behavior + iOS 兜底

95.54%

注意showModal() 会让背景 inert，但不会锁滚动。overscroll-behavior: contain 挡住滚动链，iOS 仍需记录 scrollY + position: fixed 的老办法兜底。这是个人人踩、人人重写的坑，我们一次做对。

07

无障碍当 P0 做，不当补丁

对手的空白

机会YARL 的无障碍讨论有 19 条回复，是它热度最高的帖子之一——说明这块被反复追问。

清单<dialog> 给了焦点和 ESC 的基础；再加 aria-roledescription="carousel"、切图时 aria-live="polite" 播报"第 3 张，共 12 张"、缩略图 alt 透传到大图、prefers-reduced-motion 下关掉 morph 与惯性、所有工具栏按钮有 aria-label 而不只有 tooltip。

08

组合式 API，不做插件生命周期

决策compound components 就是插件系统：加按钮 = 往 <Viewer.Toolbar> 里塞 JSX，零学习成本。只为"需要接入核心状态机"的能力（拦截手势、抢键盘）留一个受控扩展点：useViewer() 暴露状态与命令 + 可选 extensions 数组。不做生命周期、不做 context 契约。

09

触发器用 asChild，不强制我们的 <img>

理由Next.js 用户的缩略图是 next/image，Nuxt 有自己的，还有人用 <picture>。触发器必须是"转发 ref 和事件的透明包装"，而不是"我们渲染一个 img"。YARL 和 react-photo-view 在这里都有摩擦，这是低成本高回报的差异点。

配套整个组件 "use client"；缩略图本身仍可以是服务端渲染的，因为我们不接管它的渲染。

10

一个 npm 包 + 一个 shadcn registry，不分包

结构react-img-view（headless 核心，零样式）· react-img-view/styles.css（可选预设，CSS 变量暴露 token）· shadcn registry 里的 Tailwind 可拷贝源码。手势内核写成内部模块 src/core/gesture（纯 TS、零 React 依赖、独立单测），保留将来抽包的可能但现在不抽。

风险

三个可能翻车的地方

  • 手感调参没有捷径。边缘接力的阈值、阻尼系数、速度采样窗口，只能在真机上反复试。这是全项目最大的隐性成本，也是最难被别人抄走的护城河——两面性。缓解：第一周就搭起真机调试链路，不要等到最后。
  • iOS Safari 是最大未知数。<dialog> + touch-action: none + position: fixed 滚动锁 + 双指手势，这四样在 iOS 上的组合行为必须尽早验证。缓解：技术验证阶段先做一个只有手势和弹层的最小原型，在真 iPhone 上跑通再动其他。
  • 超大图分块渲染可能做不完。已经放进 P2 了，但如果早期用户就拿 8000×8000 的图来测，压力会提前到来。缓解：P0 阶段先做"上限保护 + 优雅降级"，保证不崩，不保证丝滑。

一个比截图更重要的问题

你自己最想把它用在什么场景？相册、电商商品图、文档附件、后台管理系统的图片字段——这四个场景的 P0 取舍差别很大。比如电商要放大镜和 1:1，相册要缩略图轨和幻灯片，后台要文件元信息和批量下载。定了主场景，功能优先级才有依据，不然容易做成什么都有一点、什么都不够好。
