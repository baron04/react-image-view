API 形态

三层，一层比一层往下

不做「简单版」和「专业版」两个割裂的 API。三层是同一套东西的不同装配程度——上层就是下层拼出来的，用户往下走不需要重学。

L1

单图，一行接入

覆盖 70% 场景

包一层就完事。子元素原样渲染，我们只往上挂事件和 ref——所以 next/image、<picture>、任何组件都能当触发器。

完全组合，自己拼界面

headless

L1 和 L2 的默认界面就是下面这段拼出来的。想改就把这段抄走改——shadcn registry 给的正是这段源码。

<ImageView.Root images={files} open={open} onOpenChange={setOpen}>
  <ImageView.Content>              // <dialog> + showModal
    <ImageView.Header>
      <ImageView.Close>关闭</ImageView.Close>
      <ImageView.Title />            // 当前图的 name

      <ImageView.Loading />
      <ImageView.Error />
    </ImageView.Stage>

    <ImageView.Toolbar>
      <ImageView.ZoomOut />  <ImageView.ZoomIn />
      <ImageView.RotateLeft />  <ImageView.RotateRight />

这就是「组合即插件系统」的兑现。加一个按钮不需要学插件 API，不需要注册生命周期，就是往 Toolbar 里塞 JSX。对比 YARL：加个按钮要写一个 plugin、实现它的 module 契约、再塞进 plugins 数组。

核心

手势状态机

这是全项目最难、也最值钱的一块。三层各自独立，按优先级消费同一串指针事件——关键不在分层本身，在层与层之间的交接规则。

idle
 ├─ 1 指按下 ──────────────▶ tracking      // 意图未定
 └─ 2 指按下 ──────────────▶ pinching

tracking                                   // 用首个超阈值的方向定性
 ├─ scale > fit                    ──────▶ panning
 ├─ scale = fit && |dx| > 8px     ──────▶ paging
 └─ scale = fit && |dy| > 8px     ──────▶ dismissing

panning
 └─ 该方向已到边界 && 超出量 > 40px ─────▶ paging   // ← 边缘接力

pinching  ──釋放──▶ 越界则回弹 ──▶ idle
paging    ──釋放──▶ 按速度/距离判定翻页或回弹 ──▶ idle
dismissing──釋放──▶ 按速度/距离判定关闭或回弹 ──▶ idle

边缘接力：这一条就是竞品缺的东西

// panning 每帧
const remaining = boundsX.remainingIn(direction)   // 该方向还能平移多少

if (remaining > 0) {
  applyPan(dx)                                   // 正常平移
  overshoot = 0
} else {
  overshoot += dx                                // 已顶到边，开始累计
  if (Math.abs(overshoot) > HANDOFF) {
    handoffTo('paging', { initialDelta: overshoot })   // 交棒，不中断手指
  } else {
    applyRubberBand(overshoot)                   // 交棒前给阻尼反馈
  }
}

三个细节决定手感成败：

  • 交接不能中断手指。用户的手一直没抬，从「拖动图片」变成「翻页」必须是连续的，中间出现任何停顿或跳变都会被感知为卡顿。所以 overshoot 要作为初始位移传给 paging，而不是从 0 重新开始。
  • 交棒前先给橡皮筋阻尼。顶到边之后那 40px 要有阻力反馈，用户才知道「到头了，再拖就翻页」。直接交棒会让翻页显得突然。
  • 翻页后复位到 fit。下一张图的构图和上一张无关，保留缩放没有意义——这条在设计稿里已经定了。

另外两条独立规则：下拉关闭只在 scale === fitScale 时激活，否则和平移打架；缩放上限动态算，等于原始像素 ÷ 当前渲染像素，让「放到 100%」永远可达且不越界——这是决策书里为 react-photo-view 那个浏览器崩溃 issue 定的对策。

core/ 一行 React 都不 import。这既是决策书里「保留将来抽包的可能但现在不抽」的兑现，也有当下的实惠：状态机可以脱离 DOM 渲染器做单测——喂一串合成的指针事件进去，断言状态迁移和最终 transform，不需要 jsdom，也不需要真机。手感的调参靠真机，但正确性靠这层单测兜住。

扩展点

组合解决不了的那一小类

加按钮靠组合。但「拦截手势」「抢键盘」这类要接入状态机内部的能力，组合做不到。给一个受控的小口子，只有两个钩子，没有生命周期：

type Extension = {
  name: string
  onKeyDown?(e: KeyboardEvent, api: ViewerApi): boolean | void
  onGesture?(phase: GesturePhase, s: GestureState, api: ViewerApi): boolean | void
}
// 返回 true = 已消费，停止后续处理

<ImageView.Root extensions={[measureTool]} />

刻意不做的：没有 onMount / onUnmount，没有插件间通信，没有渲染注入。需要渲染东西就用组合，扩展点只管行为。边界一模糊，这就会长成 YARL 那套插件系统。

已定

Portal 默认开，容器可指定

先厘清一件容易混淆的事：Portal 和 <dialog> 不是二选一，它们解决的是两组不相交的问题，要一起用。

问题<dialog> + showModalPortal
z-index 战争已解决 top layer 恒在最上部分缓解
祖先 overflow:hidden 裁剪已解决也能解决
祖先 transform 造成的定位偏移已解决也能解决
焦点陷阱 · ESC · 背景 inert已解决帮不上
继承祖先 font / color / line-height帮不上已解决
祖先的后代选择器命中（.panel * {…}）帮不上已解决
祖先 display:none 导致打不开帮不上已解决

top layer 把定位类问题全包了，但对样式继承类问题完全无能为力——因为元素虽然渲染在顶层，它在 DOM 树里还待在原地，祖先的可继承属性和后代选择器照常命中。而我们的主场景恰恰是后台管理系统，那里 * { font-family }、组件库全局重置、.container * 这类写法是常态。所以 Portal 默认开。

<ImageView.Root
  container={myEl}       // 可选，默认 document.body
/>

为什么必须留 container

Portal 到 body 会引入一个新问题：如果应用把主题类挂在某个嵌套容器上（<div class="dark"> 包住业务区，而不是挂在 html 上），传送出去就脱离了那个容器，暗色模式会失效。container 就是这种情况的解法——指到主题容器里，既隔离了全局污染，又保住了主题作用域。

配套的一条实现约束：我们自己的 CSS 变量定义在 :root 和 dialog 元素自身上，不依赖任何祖先 class。这样即使用户没管 container，我们的默认样式在 body 下也是完整的。

三条要写进文档的行为

  • 事件仍沿 React 树冒泡，不沿 DOM 树。预览器里的点击会冒泡到 Root 的 React 祖先，尽管 DOM 上它在 body 底下。这是 Portal 的既定行为，通常正合需要（上下文、表单都还能用），但会让第一次遇到的人困惑。
  • SSR 期间不渲染。container 要等 document 存在，所以挂载前返回 null。因为预览器只在打开时才挂载，这不产生首屏影响。
  • showModal() 在 layout effect 里调，早于浏览器绘制，避免闪一帧未模态的状态。

运行时架构

写状态机之前必须先定的五件事

前面几节定的是公开 API——外面怎么用。这一节定的是运行时——里面怎么跑。两者独立：API 再清楚，也回答不了「每帧的 transform 提交到哪里」。而这五条每一条做错，代价都是重写而不是重构。

一 · 变换提交路径：手势期间绕开 React

手势期间 transform 每帧都变。走 setState 等于每秒 60 次重渲染整棵子树，在低端安卓上必然掉帧。

决策：transformRef 是唯一真相，手势期间直接写 DOM，静止后才同步回 React state。

// 手势中 —— 不碰 React
transformRef.current = next
imgRef.current.style.transform =
  `translate3d(${next.x}px, ${next.y}px, 0) scale(${next.scale}) rotate(${next.rotation}deg)`

// 静止后 —— 同步一次，驱动按钮的 disabled / data-active
setTransform(transformRef.current)

这带来两份状态，必须明确各自的职责边界：ref 供渲染，state 供 UI 反馈。工具栏按钮的可用性不需要每帧精确——用户不会在甩动图片的中途去看放大按钮灰没灰。命令式操作（点按钮、按快捷键）则两者同时更新。

二 · 轨道模型：两层 transform，互不干涉

边缘接力要求「拖到头继续拖就翻页」是连续的，那么下一张图在手指还没抬起时就必须已经在 DOM 里、且可见。所以不能只渲染当前图。

决策：渲染窗口 [index-1, index, index+1]，轨道横向平移。关键在于两层 transform 分工：

<div class="track">              ← 第 1 层：翻页　translateX
  <div class="slide"><img/></div>    index - 1
  <div class="slide"><img/></div>  ← 第 2 层：缩放 + 平移在 img 上
  <div class="slide"><img/></div>    index + 1
</div>

track.style.transform = `translate3d(${-index * 100 + dragPercent}%, 0, 0)`
img.style.transform   = `translate3d(${x}px, ${y}px, 0) scale(${s})`

缩放平移作用在 img，翻页作用在 track。边缘接力因此不是「切换模式」，只是把每帧的位移从内层记账改成外层记账——两层始终并存，永远不需要中断或重置任何一层。这是让交接感觉不到接缝的根本原因。

三 · 坐标系：一次说清，否则处处出错

  • transform.x / y —— 以舞台中心为原点的 CSS 像素偏移。{x:0, y:0} 即居中。
  • transform.scale —— 相对原始像素。scale === 1 即 1:1。
  • 缩放锚点 —— 指针事件给的是 client 坐标，进 zoomAbout 前必须换算：origin = client − stageRect 中心。
  • 轨道位移用百分比不用像素，这样窗口 resize 时不需要重算。

四 · 动画所有权：一个 Ticker，用户输入永远优先

同时可能存在的动画有四种：开合 FLIP、缩放回弹、平移惯性、翻页吸附。各自起一个 requestAnimationFrame 会互相打架——两个循环同时写同一个 style.transform，结果取决于调用顺序。

决策：单一 Ticker，所有动画向它注册；任何 pointerdown 无条件取消全部在跑的动画。用户的手指永远赢——中途接管一个正在回弹的图片，必须立刻跟手，而不是等动画放完。

五 · 预加载：按 index 驱动，不用 IntersectionObserver

常见做法是 IntersectionObserver，但预览器里三张图始终都在视口内，观察器给不出有用信号。决策：以 index 变化为触发源，预加载前后各一张；切换时若目标图未 decode 完，保持当前图并显示加载态，不留空白。这正是 core/image.ts 里 decode-before-swap 的用武之处。

五条定完，状态机才有地方落。迁移函数要写成纯函数——输入 (state, event, context)，输出 (nextState, commands)，自己不碰 DOM、不碰 rAF。副作用由 React 绑定层执行。这样状态机能脱离浏览器做单测：喂一串合成指针事件，断言相位迁移和最终 transform，不需要 jsdom，也不需要真机。

要先想清楚的

两个还没定的问题

  • 触发器怎么拿到 index。按挂载顺序自动登记最省事，但 React 并发渲染下顺序不保证稳定。备选是要求显式传 index，啰嗦但确定。倾向：自动登记为主，显式 index 可覆盖。
  • 预设样式用 CSS 还是 Tailwind。npm 包附 styles.css（不依赖 Tailwind，谁都能用），registry 给 Tailwind 版源码。两份要保持同步，是一笔持续成本——但这正是同时吃到「装包即用」和「拷贝即改」两种分发的代价。
