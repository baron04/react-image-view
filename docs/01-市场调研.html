又一个灯箱值得做吗

对 19 个图片预览开源库的下载量、维护状态、许可证与未修缺陷做了一轮取数。结论是：市场正在高速增长，但这个品类拿不到 star——除非换一个做法。

如果目标是 star：这是最差的品类之一。基础 UI 件是"选一次、忘掉"的东西，开发者不会为它兴奋。现任冠军四年只攒了 1,304 star，而周下载 54.7 万。

如果目标是"做出真被用的东西 + 技术声誉"：值得，但必须换切入点。正面做通用灯箱要对上一个 open issue 常年为 0、文档站完备、支持 React 19 的强维护者，赢面很小。真正空着的是三个位置：宽松许可证的高完成度方案、headless 架构、以及底层手势内核。

缺陷取证

三个头部各自的硬伤

yet-another-react-lightbox —— 强，但有两处结构性缺口

必须先承认它做得好：零运行时依赖、11.7 kB gzip、React 16.8→19 全支持、按插件分包（./plugins/zoom 等 10 个子路径导出）、sideEffects 标注正确、open issue 只有 1 条（还是 Renovate 的 Dependency Dashboard）。这是一个被认真运营的项目。

但它的 Discussions 里，两条讨论热度明显高于其余：

  • 不支持旋转——"Image rotation" 是票数最高的讨论（7 赞 / 12 回复），至今官方插件列表里没有。而 react-photo-view 通过 overlayRender 暴露 rotate，早就能做。
  • 无障碍是一条 19 回复的长贴——热度最高的讨论之一，说明 a11y 上存在被反复追问的空白。
  • "Zoom blocks swipe until fully zoomed out"——放大后必须完全缩回才能滑到下一张。这是手势状态机分层没做好的典型症状，在手机上是每天都会碰到的体验缺陷。
  • 另有"拖动缺少惯性"、"嵌在 Dialog 里有问题"、"Android 上与地图同屏闪烁"等未解决讨论。

另外一处不在 issue 里但对现代项目很关键：它的定制走 CSS 变量 + class 覆盖，不是可组合的 parts。任何有设计系统的团队要让它匹配自己的 token，都得跟它的样式表打一架。

react-photo-view —— 手感最好的那个，正在失修

7.5 kB gzip，边缘回弹、双指定点缩放、开合动画衔接，移动端手感公认第一。问题全在维护上：最近提交停在 2026-01-30，64 条 open issue 里躺着的是硬伤——大尺寸图导致浏览器崩溃、iOS 双指缩小回弹抖动、连续 ESC 关闭后状态异常、无法编程式打开、不支持返回键关闭、文档站（vercel.app）曾经打不开。它的 issue 区中英混杂，实际是单人项目，bus factor = 1。

值得注意的是它的 star 效率是 YARL 的 8 倍：97k 周下载换来 1,893 star（51:1），而 YARL 是 420:1。原因大概率是中文社区传播 + README 里那张手势 GIF 太有说服力。这是本次调研里对"怎么拿 star"最有用的一条情报。

react-zoom-pan-pinch —— 下载量最大，守得最松

223 万周下载，是所有灯箱加起来还多的量级，但 132 条 open issue，且都是核心能力上的：3.6.1 版本 pinch 直接失效、macOS 双指无法平移、大图缩放卡顿、不支持旋转、Shadow DOM 下不可用、无 CSP nonce 支持、限位与 resize 交互不正确。热度第一的 issue 是 2023 年的"👋 谁在用"，路线图贴停在 2023 年。

换句话说：真正被大量使用、又真正没被照顾好的，是底下那层"手势 + 变换"内核，不是上面那层灯箱 UI。

机会

三个空位

许可证

功能最全的两个都不能白用

Fancybox 是商业许可，lightGallery 是 GPLv3 或买断。它们才是"缩略图轨 + 深链 + 全屏 + 混合媒体 + 物理手势"这一档完成度的代表。这一档里没有 MIT 的 React 原生方案。

证据：@fancyapps/ui = "SEE LICENSE IN LICENSE.md"；lightgallery npm license = GPLv3。合计 18 万周下载在找出路。
架构

headless 赛道完全空置

生态早就转向 headless + 复制粘贴（Radix Dialog 7,227 万周下载，vaul 4,065 万）。但灯箱这一格里，唯一的 headless 尝试只有 1 star。所有现存方案都是"给你一套样式，你来覆盖"。

证据：@hanakla/react-lightbox = 1 star。YARL / react-photo-view 均为带样式表的成品组件。
底层

手势内核没人做对

react-zoom-pan-pinch 用 223 万周下载证明了需求，用 132 条 issue 证明了没做好。做一个正确的 pinch / pan / 惯性 / 回弹 / 边界内核，受众远不止图片预览——地图、图表、PDF、白板都要。

证据：pinch 失效、mac 双指、大图卡顿、Shadow DOM、CSP nonce 均为长期未修 issue。

如果我们来做

三条路线

路线 A：分层——手势内核 + headless viewer + 可拷贝皮肤

推荐

不做"第 21 个灯箱"，做一个三层的东西，每一层都能独立被人用。这样即使上层灯箱打不过 YARL，下层内核仍然吃得到 react-zoom-pan-pinch 那 223 万下载的盘子。

  • 底层｜手势与变换内核：纯 Pointer Events 状态机，pinch / pan / wheel / 双击 / 惯性 / rubber-band 回弹 / 边界约束；支持 Shadow DOM、CSP nonce、SSR。这一层单独发包，直接对标 react-zoom-pan-pinch 的未修清单。
  • 中层｜headless 组合式组件：<Viewer.Root> / .Slide / .Toolbar / .Thumbs，零样式，Radix 式 asChild，受控与非受控双支持。设计系统团队直接套自己的 token，不用跟样式表打架。
  • 上层｜shadcn registry 皮肤：npx shadcn add image-viewer 一行拷进项目，用户拿到的是可改的源码而不是黑盒。这是当下最有效的分发路径。
  • 差异化功能（全部是竞品明确缺的）：旋转；放大态下仍可滑动切图（分层状态机解掉 YARL 那个缺陷）；惯性与回弹；URL / History 深链；View Transitions API 做缩略图→大图 morph；真无障碍（焦点陷阱 / aria-roledescription / 屏幕阅读器播报 / prefers-reduced-motion）；EXIF 方向；超大图分块渲染（解掉 react-photo-view 崩浏览器）。

路线 B：接管 react-photo-view 的生态位

风险中

它手感最好、star 效率最高、但停更 7 个月且积压 64 条 issue。把这些硬伤修对并持续维护，能直接继承它那 9.7 万周下载的迁移需求。

  • 成本最低、验证最快，因为需求已经被它证明过了。
  • 风险是原作者随时可能回来——一次提交就能让这条路线失去意义。
  • 更稳的变体：先给它提 PR，从贡献者做起，同时把内核抽成独立包。

路线 C：不发库，只发一个 shadcn block

成本最低

把预览组件做成 registry 里的一段可拷贝源码，投放到 awesome-shadcn-ui 等聚合入口。

  • 传播最快、维护负担最小，但 star 上限也最低，且几乎不产生技术壁垒。
  • 适合当作路线 A 的第一步：先用 block 验证审美和手感，再往下沉内核。

期望管理

容易拿 star 吗：不容易，说清楚为什么

直说结论：这个品类的 star 转化率极低。看这三组比值——

每 400 次周下载才换来 1 个 star，因为基础 UI 件是装完就忘的东西。现实预期：第一年 200–800 star 算好结果，两三年做到 2k 就已经是这个品类的冠军量级。如果目标是一年冲几千 star，应该换品类，不是换做法。

但 react-photo-view 的 51:1 说明 star 效率可以差出 8 倍，杠杆在这三处：

  • 用架构定位，而不是用功能定位。开发者会为"headless / 手势内核"点赞，不会为"又一个灯箱"点赞。README 第一句话决定这件事。
  • 做一张能自证的 GIF。手势物理感和 View Transitions 的 morph 是天然的传播素材——react-photo-view 那张 GIF 就是它 star 效率的来源。
  • 吃分发渠道，而不是等搜索。shadcn registry、awesome-* 列表、中文技术社区。中文社区对这个品类的 star 贡献被 react-photo-view 验证过。

下一步

建议的讨论顺序

调研到此为止。接下来要定的是三件事，建议按这个顺序：

  • 先定路线（A / B / C），因为它决定了后面所有取舍——尤其是"要不要把手势内核单独发包"这个分层决策。
  • 再定功能边界：旋转、放大态滑动、深链、a11y、超大图这五项是差异化核心；缩略图轨、幻灯片、下载、分享、视频这些是补齐项，可以后置。
  • 最后定架构：状态机怎么分层（这直接决定能不能解掉 YARL 那个"放大后不能滑动"的缺陷）、headless 的 parts 怎么切、包怎么拆。
